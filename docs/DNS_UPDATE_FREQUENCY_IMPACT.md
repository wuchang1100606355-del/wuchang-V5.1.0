## 🔍 DNS TTL 基本概念

### TTL（Time To Live）定義

TTL 是 DNS 記錄的生存時間，單位為秒。它決定了：
- DNS 記錄在 DNS 伺服器和客戶端緩存中保留的時間
- DNS 記錄更新的傳播速度
- 系統對 DNS 變更的響應時間

### 常見 TTL 值

| TTL 值 | 時間 | 適用場景 |
|--------|------|----------|
| 60 | 1 分鐘 | 頻繁變更、測試環境 |
| 300 | 5 分鐘 | 快速更新、開發環境 |
| 600 | 10 分鐘 | 一般更新、測試 |
| 3600 | 1 小時 | 標準生產環境 |
| **5400** | **90 分鐘** | **當前設定（平衡更新速度和檢查頻率）** |
| 86400 | 24 小時 | 穩定生產環境 |

## ⚡ DNS 更新頻率對系統的影響

### 1. 對每小時檢查系統的影響

#### 當前設定（每小時檢查）

**影響分析**：

- ✅ **TTL = 300 秒（5 分鐘）**
  - 優點：DNS 變更可在 5 分鐘內生效
  - 缺點：DNS 查詢頻率較高，可能增加 DNS 伺服器負載
  - 適用：開發和測試環境

- ✅ **TTL = 3600 秒（1 小時）**
  - 優點：與每小時檢查頻率匹配，減少不必要的 DNS 查詢
  - 缺點：DNS 變更需要最多 1 小時才能完全生效
  - 適用：標準生產環境

- ✅ **TTL = 5400 秒（90 分鐘）** ⭐ **當前設定**
  - 優點：平衡更新速度和查詢頻率，略長於檢查頻率提供緩衝
  - 優點：減少 DNS 查詢頻率，同時保持合理的更新速度
  - 缺點：DNS 變更需要最多 90 分鐘才能完全生效
  - 適用：生產環境（已採用）

- ⚠️ **TTL = 86400 秒（24 小時）**
  - 優點：DNS 查詢頻率最低，減少伺服器負載
  - 缺點：DNS 變更需要最多 24 小時才能完全生效
  - 適用：非常穩定的生產環境

#### 每小時檢查系統的建議

**當前設定**：`TTL = 5400 秒（90 分鐘）` ✅

**原因**：
1. 略長於每小時檢查頻率，提供緩衝時間
2. 平衡了更新速度和查詢頻率
3. 減少不必要的 DNS 查詢（比 300 秒減少約 82%）
4. 適合生產環境使用

### 2. 對網域部署的影響

#### 快速部署場景

**TTL = 300 秒（5 分鐘）**

**優點**：
- ✅ DNS 變更快速生效
- ✅ 適合快速切換 IP 地址
- ✅ 適合故障轉移（Failover）場景

**缺點**：
- ❌ 增加 DNS 查詢頻率
- ❌ 可能增加 DNS 伺服器負載
- ❌ 客戶端緩存時間短，可能影響性能

#### 穩定部署場景

**TTL = 3600 秒（1 小時）**

**優點**：
- ✅ 平衡更新速度和性能
- ✅ 減少 DNS 查詢頻率
- ✅ 符合標準生產環境

**缺點**：
- ⚠️ DNS 變更需要最多 1 小時生效
- ⚠️ 不適合需要快速切換的場景

### 3. 對憑證簽發的影響

#### Let's Encrypt 證書申請

**DNS-01 驗證方式**：

- **TTL = 300 秒（5 分鐘）**
  - ✅ ACME 挑戰記錄快速生效
  - ✅ 證書申請速度較快
  - ⚠️ 需要等待 TTL 過期才能驗證

- **TTL = 3600 秒（1 小時）**
  - ⚠️ ACME 挑戰記錄需要較長時間生效

**建議**：
- 證書申請時：臨時降低 TTL 到 300 秒
- 證書申請後：恢復 TTL 到 3600 秒

## ⚠️ 注意事項

### 1. DNS 緩存影響

- 即使 TTL 較短，客戶端和 DNS 伺服器仍可能緩存記錄
- 實際生效時間可能比 TTL 更長

### 2. 每小時檢查系統

- 當前每小時檢查一次
- TTL 應該與檢查頻率匹配或更長
- 避免 TTL 過短導致檢查結果不一致

### 3. Google Cloud DNS

- Google Cloud DNS 支援動態 TTL 調整
- 可以根據場景臨時調整 TTL
